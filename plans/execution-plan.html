  • Why this works with what exists: the Cloudflare Worker already serves every version from one origin (seanmh.com) via transparent proxy + pv cookie + ?v= override. Same-origin is the requirement for cross-document View Transitions, so cinematic switching needs zero architecture change — only CSS/JS in each version and a small worker extension for clusters.
  • Each new page = a new version/* branch + Pages deployment, same as today. Shared assets flow through the existing content branch sync.

Phase 1 — Cinematic In-Cluster Switching

  1. Switcher kit (on content branch, synced to all versions): a "universe dial" component + a shared identity element (name/avatar "Sean card") present in every version, tagged view-transition-name: sean-card.
  2. Cross-document View Transitions: add @view-transition { navigation: auto; } to each version. Switching navigates to /?v=<name> (existing worker override) — the Sean card morphs between layouts; the rest crossfades with per-version flavor via transition types (e.g. terminal exits with a CRT power-off, card flips).
  3. Progressive enhancement: Safari/Firefox without cross-document VT get a clean ~200ms CSS fade fallback; prefers-reduced-motion disables all of it.
  4. Worker touch-up: bump pv cookie max-age on every response (not just first visit) so the chosen version sticks through a browsing session.
Verify: dial appears in all 3 versions · morph works in Chrome desktop + Android · Safari/Firefox fall back without breakage · cookie stickiness intact · Lighthouse perf within 5 pts of baseline.

Phase 2 — Make the Terminal Real

  1. Command engine on version/c-terminal: help, ls projects, cat resume.md, open <project>, git log (real history baked in at build), switch <version> (triggers Phase-1 transition), command history (↑/↓) and tab completion. Content sourced from the content branch so it never drifts from the other versions.
  2. ask <question>: worker route /api/ask → Claude API (Haiku 4.5, streaming SSE) with a system prompt grounded in resume + project content. The worker handles /api/* itself before proxying.
  3. Guardrails: per-IP rate limit (Workers KV, ~10 req/hr), max-token cap, API key in worker secret, prompt scoped to "answer about Sean only."
Verify: all commands + completion + history work · ask streams a grounded answer in <3s to first token · rate limit returns friendly message · key never reaches client · off-topic questions politely refused.

Phase 3 — The Shiny Button, the Bridge & Cluster 2's First Page

  1. Worker v2 — cluster model: config becomes two clusters. pv cookie still picks within Cluster 1 on first visit; a visitor's current page determines which "adjacent" versions the dial offers. Cluster 2 is never randomly assigned — it's only reachable through the button (it should feel like a discovery).
  2. The shiny button: one irresistible artifact in all Cluster-1 versions (glowing orb in the corner; in the terminal it's a mysterious ??? command that help hints at). Subtle idle animation, stronger pull on hover.
  3. The bridge transition: deliberately different from in-cluster morphs — a warp/iris-wipe (View Transition types: ['bridge']) so crossing clusters feels like leaving the universe, not flipping a page. Same effect in reverse to come home.
  4. Cluster 2 page #1 — The Hall of Versions (version/d-hall): gallery of AI-generated site designs; each entry = screenshot, generation #, date, and the prompt that created it. Ships with generation #1 created interactively with Claude Code.
  5. Self-redesign pipeline: monthly scheduled Claude Code cloud agent (or GitHub Action): pick a style direction → generate a full standalone design as gen/N branch → open PR with preview link. On merge: deploy, screenshot, append to the hall manifest. Human approval stays in the loop — a PR you review.
Verify: button visible in all 3 v1 versions, never randomly assigned into Cluster 2 · bridge warp distinct from in-cluster morph, works both directions · hall renders gen #1 · pipeline produces one real merged PR end-to-end · direct URL to Cluster 2 still works (deep links).

Phase 4 — The Nexus

  1. version/e-nexus: a single lightweight Three.js scene — floating portals, one per page across both clusters; drag to orbit, click/tap a portal to travel (portal zoom blends into the View Transition).
  2. Budget: <1 MB JS gzipped, lazy-load the scene behind an instant-paint title frame, static image + link list fallback for WebGL-less devices.
  3. Wire into the Cluster-2 dial (d-hall ⇄ e-nexus).
Verify: interactive in <2s on simulated 4G mid-tier phone · all portals navigate correctly · fallback renders without WebGL · 60fps orbit on desktop.

Phase 5 — Third Cluster-2 Page + Polish (decide later)

  • Polish pass: per-version OG images, version-assignment analytics, accessibility audit, wiki docs update.

Risks & Mitigations

  • Cross-document View Transitions aren't universal
  • → Treat as enhancement; fade fallback everywhere; feature-detect, never block navigation.
  • Claude API cost/abuse on ask
  • → Haiku model, KV rate limit, token caps, monthly spend alert.
  • Six+ deployments drifting out of sync
  • → All shared content/components live on content branch; sync workflow is the only path in.
  • Nexus bloating load time
  • → Hard 1 MB budget enforced in CI; it's a destination page, never the random landing.
