Written July 2026. Scope: version/a-scroll only (worktree wt/a-scroll). Goal: turn the scroll version from a polished-but-static page into a scroll-driven cinematic experience — the version that earns its name. Companion to plans/continuation-plan.html.

Where a-scroll is today

  • Four static sections: Hero → About → Experience → Contact, each a simple py-24 block inside max-w-4xl.
  • The only motion is a one-shot CSS fade-in stagger in the hero on page load. Nothing responds to scrolling.
  • Stack: Astro 5.17, Tailwind 4.2, no animation libraries. Phase 1 switcher kit is present (VersionSwitcher.astro, transitions.css, vt-sean-name/vt-skip-intro tags on the hero headline).

Inspiration → concrete techniques

Two reference points, each contributing different moves:

SourceWhat makes it workWhat we steal
apple.com product pages Pinned "scenes": a section sticks to the viewport while scroll scrubs a transformation (text fades through beats, product rotates/zooms). Animation always serves a narrative; between scenes the page scrolls normally. Restraint — few effects, executed perfectly. One pinned, scrubbed story section; scroll-linked text beats; the discipline of "normal scrolling between set pieces."
landonorris.com (OFF+BRAND, Awwwards Site of the Month) Speed-inspired cinematic scrolling: buttery smoothed scroll, oversized kinetic typography, velocity-reactive motion, image reveals, bold stat callouts, WebGL/Rive accents — but kept performant via lazy-loading and tight budgets. Smoothed scroll feel; oversized hero typography that reacts to scroll; velocity-based accents; clip-path image reveals; big stat counters. (We skip WebGL/Rive — that's the Nexus's job in Phase 4.)

Guiding principle: a-scroll is still a portfolio — the content must be fully readable if every effect is stripped away. Motion is choreography on top of a working document, never a gate in front of it.

Decision: motion stack

Option A — GSAP ScrollTrigger + Lenis RECOMMENDED

  • GSAP (incl. ScrollTrigger, SplitText) has been 100% free — including formerly-paid plugins — since the Webflow acquisition (2025). It is the industry standard behind most Awwwards scroll work, including sites like landonorris.com's genre.
  • ScrollTrigger gives pinning, scrubbing, staggered reveals, and velocity access with one mental model. Lenis (~4 KB) supplies the smoothed scroll feel; GSAP's own ScrollSmoother is an alternative but Lenis is lighter and plays well with native anchors.
  • Budget: gsap core + ScrollTrigger + SplitText + Lenis ≈ 60–75 KB gzipped, loaded once as an Astro client script. Acceptable for a page whose whole identity is scroll.

Option B — CSS scroll-driven animations only lighter, weaker

  • animation-timeline: view()/scroll() + position: sticky + IntersectionObserver. Zero dependencies; reveals and parallax are easy.
  • But multi-beat pinned scenes, scrub easing, split-text choreography, and velocity effects get awkward fast, and support (verify at build time) is still not universal — meaning fallback code anyway.

Call: Option A. One system for everything, guarded by prefers-reduced-motion. If we later regret the JS weight we can migrate the simple reveals to CSS timelines without redesigning.

Cross-cutting constraints (read before every phase)

  • Reduced motion is a hard off-switch. With prefers-reduced-motion: reduce: no Lenis, no pins, no scrubs; everything renders in its final visible state. Implement as an early return in the init module, not per-effect.
  • Don't break the Phase 1 kit. VersionSwitcher.astro and transitions.css stay byte-identical to the other branches — new effect CSS goes in a new file (e.g. src/styles/scroll.css). The hero headline keeps vt-sean-name vt-skip-intro; the name morph on version switch must keep working, so on arrival via view transition (vt-arrived class) skip intro animations the same way the current fade-in does — extend that convention to all new intro effects.
  • Anchors must work. #contact, #about, scroll-padding-top, and the nav all currently rely on native smooth scroll. Lenis must be wired to handle anchor navigation (its scrollTo) — verify this specifically, it's the classic smooth-scroll regression.
  • Performance: animate transform/opacity/clip-path only; no scroll-linked layout properties. Pinned sections reserve their scroll distance (no CLS). Target: Lighthouse perf within 5 pts of current baseline, 60 fps scrub on an M-series Mac and a mid-tier Android.
  • Mobile is first-class. Test iOS Safari early — rubber-banding + Lenis + pinning is where these builds die. Pins may shorten or degrade to simple reveals below md.
  • SEO/a11y: all content in the DOM at build time; effects only hide-then-reveal (initial hidden state applied via JS, not CSS, so no-JS visitors see everything).
  • Branch hygiene: all work commits to version/a-scroll. New shared content (e.g. projects.ts) lands on content first, then cherry-picks in — per the content contract. Version-specific components/styles stay on the branch.

Phase S1 — Motion foundation

  1. Add deps to the branch: gsap, lenis.
  2. Create src/scripts/scroll.ts: single entry that (a) bails on reduced motion, (b) boots Lenis and bridges it to ScrollTrigger (lenis.on('scroll', ScrollTrigger.update) + gsap ticker), (c) registers all effects, (d) exposes teardown. Load from BaseLayout.astro with <script> (this version is a single page — init on load and on pagereveal arrival is enough).
  3. Wire anchor links through Lenis; confirm scroll-padding-top equivalent offset.
  4. Add a thin scroll-progress bar (accent color, top of viewport) as the first visible proof the system works.
Verify: smoothed scroll feels right on trackpad + wheel + touch · #contact nav links land correctly · reduced-motion gets 100% native behavior · progress bar tracks · no console errors on version-switch arrival · build passes.

Phase S2 — Hero set piece (the first impression)

Pin the hero for ~1.5 viewport-heights of scroll and scrub a transformation, landonorris-style oversized type included:

  • Upgrade the name to oversized display type (clamp up to ~10rem, tight tracking) — it's the identity element that morphs between versions, so bigger = a better morph too.
  • Scrub timeline: "Hello, I'm" drifts up and fades → name scales down slightly and letter-spacing expands → title/tagline parallax at different rates → gradient-mesh orbs drift oppositely (depth) → a "scroll" cue (chevron/line) that fades immediately on first scroll.
  • Release the pin into About with a slight overlap (About's heading starts revealing before the hero fully leaves).
  • Keep the existing load-in fade stagger as the pre-scroll intro (skipped on vt-arrived, as today).
Verify: pin reserves space (no jump/CLS) · scrub is 60fps · name morph from b-card/c-terminal still lands on the (now larger) headline cleanly · mobile either pins gracefully or degrades to parallax-only · reduced motion = static hero.
Gotcha: view-transition-name on an element inside a transformed/pinned container — take an arrival screenshot test through the dev proxy before polishing further.

Phase S3 — Section choreography (reveals & kinetic details)

  • SectionHeading: heading masks in from below (SplitText line reveal); its underline/rule draws left→right on enter.
  • About: headshot reveals with a clip-path wipe + subtle parallax drift; paragraphs reveal line-by-line with a soft mask (Apple-style text beats, triggered — not scrubbed).
  • Experience: a vertical timeline rule that draws with scroll progress through the section; each ExperienceItem rises/fades staggered as it enters; dates/company names get a slight secondary parallax.
  • Contact: oversized "Get in touch" line (biggest type on the page after the hero) revealed with a mask; the button gets a magnetic-hover microinteraction.
  • All reveals fire once (no re-hiding on scroll-up) — re-triggering reads as gimmicky.
Verify: every section fully legible with JS disabled · reveals fire exactly once at sensible thresholds · SplitText respects wrapping at all breakpoints (re-split on resize) · dark + light themes both clean.

Phase S4 — Signature pinned story NEEDS CONTENT

The Apple-style centerpiece: a new full-viewport section between About and Experience that pins and scrubs through 3–4 narrative beats. Two candidate shapes — pick when content exists:

  1. "By the numbers" story: pinned dark stage; each beat is a short statement + a huge animated stat (counters scrub with scroll), e.g. years building, systems shipped, scale handled. Punchy, needs only facts.
  2. Projects strip: pinned section that translates horizontally through 3–5 project cards (screenshot, name, one-liner, link) — the landonorris gallery move. Richer, needs real project assets. Content would live in src/content/projects.ts on the content branch so other versions can adopt it later.
Content ask (Sean): to unlock this phase —
· 3–5 projects: name, one-line description, link (repo or live), and a screenshot/image each (for shape 2)
· 3–4 true stats/facts worth shouting (years, scale, favorite numbers) (for shape 1)
· Optional: any high-res imagery you'd enjoy seeing parallaxed (workspace, art, snowboarding, Sunny the cat).
Verify: pinned scene enters/exits without jump · beats readable at every scroll speed (no skipped states on fast flicks) · horizontal strip (if chosen) works with touch + trackpad + keyboard · section is skippable and screen-reader-sane (content is ordinary DOM under the hood).

Phase S5 — Ambient polish & ship

  • Velocity accents: tie scroll velocity to a subtle skew or parallax intensity on large type (cap it — 2–3° max).
  • Marquee strip: an infinite skills/interests ticker (velocity-reactive direction/speed) as a section divider.
  • Nav: backdrop-blur + shrink after the hero releases; active-section indicator driven by the same ScrollTriggers.
  • Easing pass: one shared ease vocabulary (e.g. power2.out for reveals, linear for scrubs); remove any effect that hasn't earned its place — Apple's restraint is the bar.
  • Full QA matrix: Chrome/Edge/Safari/Firefox desktop · iOS Safari + Android Chrome · reduced motion · light + dark · version-switch arrival/departure morphs · Lighthouse vs baseline · no-JS render.
  • Update wiki (wiki/) with a new Scroll-Experience.md: stack, init/teardown pattern, kit-interaction rules. Push version/a-scroll when Sean gives the go-ahead.
Verify: QA matrix green · Lighthouse within 5 pts · JS payload delta ≤ ~80 KB gz · the page still reads as a portfolio first, showpiece second.

Risks & mitigations

  • Lenis vs. anchors/view-transitions: smooth-scroll libs historically break hash links and scroll restoration. → Route anchors through Lenis explicitly; test arrival scroll position after a version-switch morph; kill Lenis on reduced motion.
  • Pinning on iOS Safari: jank and address-bar resize chaos. → Test S2 on a real iPhone before building S4; be willing to degrade pins to static + reveal on small screens.
  • Effect creep: every technique in this doc on one page = a theme park. → Each phase ends with a "remove what hasn't earned its place" pass; Apple restraint is the tiebreaker.
  • Kit drift: tempting to tweak transitions.css for the new hero. → Any kit change goes to content first and cherry-picks to all three versions, or doesn't happen.
