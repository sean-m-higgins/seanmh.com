Cookie nuance (already handled): worker.js and dev-proxy.mjs only set the pv cookie when Sec-Fetch-Dest: document (or Accept includes text/html). This stops a stale in-flight asset request from the old version overwriting a just-switched cookie. Preserve this if you touch cookie logic.

Phase 3 — Shiny button, bridge transition, Cluster 2 + Hall of Versions

  • Worker v2 cluster model: VERSIONS array becomes two clusters. Cluster 1 (scroll/card/terminal) keeps random assignment + pv cookie. Cluster 2 is never randomly assigned — only reachable via the button (it's a discovery). The dial offers only same-cluster neighbors based on current page.
  • Shiny button: one irresistible artifact in all Cluster-1 versions (glowing corner orb; in the terminal it's the hidden command help hints at — wire this into the Phase 2 registry).
  • Bridge transition: deliberately distinct from in-cluster morphs — a warp/iris-wipe via a types: ['bridge'] view-transition type, both directions. Reuse the Phase 1 pageswap/pagereveal plumbing; add a bridge type branch in transitions.css.
  • Hall of Versions (version/d-hall + new Pages project): gallery of AI-generated designs — screenshot, generation #, date, the prompt that made it. Ship with gen #1.
  • Self-redesign pipeline: scheduled Claude Code cloud agent / GH Action → generates a gen/N branch → opens a PR with preview. On merge: deploy, screenshot, append to hall manifest. Human approval stays in the loop.

Phase 4 — The Nexus (version/e-nexus)

  • One lightweight Three.js scene: floating portals, one per page across both clusters; drag-orbit, click/tap to travel (portal zoom blends into the view transition).
  • Hard budget: <1 MB JS gzipped; lazy-load behind an instant title frame; static image + link-list fallback for no-WebGL. Never the random landing page.
