Version G — United States places

Design plan, September 19, 2026. Built September 20, 2026. Temporary feature plan for version/g-travel.

Goal: begin filling in the United States on the travel atlas — many individual places, entered gradually, each shading the state it sits in.

Status: all four steps are built and verified against the first 42 places. What follows is the design as built; the open items are at the foot.

Temporary: this file exists only while the work is being executed. When it ships, the durable facts go to the wiki (Travel.md) and the open items to plan.html, and this file is deleted. plan.html stays the only standing plan.

Why a second data layer

The atlas models travel as journeys: four trips across three European countries in src/content/trips.ts, one globe marker per trip anchor and one great-circle route per trip. That shape does not fit the United States. Most American places were never part of a named journey, there will be far more of them than of trips, and the content arrives over months rather than in one sitting.

So the US gets a places layer alongside journeys — lighter, flatter, and with no journal page or photo gallery behind it — plus visited-state shading so the country reads as coverage rather than as a scatter of lights. The journey model is not touched.

What existed before this work

✓ Data and validation

src/content/trips.ts holds countries and trips; validateTravelData in globe-utils.mjs throws at build time from TravelGlobe.astro.

✓ Globe

globe.ts rasterises countries-110m.json to a 2048×1024 canvas texture, draws one marker group per trip and one tube route per trip.

↻ Homeland shading in flight

Uncommitted isHomelandPolygon work stopping French Guiana and Svalbard from reading as visited, touching the same painter this plan edits. It has since been committed as 4a60657.

! No place entity

There is no pin below the level of a trip anchor, no subdivision data, no US record, and no label rendering on the globe.

Decisions

QuestionDecisionWhy
How is the US represented? City pins and shaded states. Pins alone under-read the amount of ground covered; fills alone lose the specific places.
How do dense pins stay readable? A hairline “laser beam” mark, not the journey marker. No clustering and no level-of-detail logic to build or tune. See Beam pins.
What content per place? Name, date, optional one-sentence note. Low enough friction that the list can actually be filled in. No prose, no photos, no page.
Where does it live? The existing /travel/ hub. No new pages. Places are not journeys; a page per place would be a hundred thin pages.

The design

1. Data layer — a places export

Added to src/content/trips.ts, which already holds the countries, the trips, and their lookup helpers:

export interface PlaceRecord {
  id: string;        // "seattle" — unique, kebab-case
  label: string;     // "Seattle"
  state: string;     // "Washington" — must match a us-atlas state name exactly
  latitude: number;
  longitude: number;
  date?: string;     // "2019" | "2019-07" | "2019-07-14" — any precision
  note?: string;     // one sentence, optional
}

export const places: readonly PlaceRecord[] = [];
export function placesForState(state: string): readonly PlaceRecord[];
  • state is the full name, not a two-letter code, because it is the join key to the atlas (properties.name in us-atlas). That removes a fifty-row abbreviation-to-FIPS table that would otherwise need authoring and maintaining.
  • date is optional and variable-precision. A place remembered only by year should not be blocked from entry. A formatPlaceDate() helper renders 2019 / July 2019 / 14 July 2019.
  • No publication gate, unlike TripRoute.published. A place is published when it is committed; a half-remembered one simply stays out of the file.

The US also joins countries, with one new optional field on CountryRecord:

{ iso2: "US", atlasId: "840", name: "United States",
  centroid: { latitude: 39.8, longitude: -98.6 }, shadeBy: "states" }

2. State fills

  • Add us-atlas as a devDependency. It is read at build time only; the client never downloads it.
  • New build-time module src/content/us-states.mjs exporting stateShapes(names) → { shapes, errors }. It reads us-atlas/states-10m.json, converts it with the already-installed topojson-client, returns rings for the named states, and reports unknown names through the same throw new Error("Invalid travel content: …") path already wired into TravelGlobe.astro.
  • First step: confirm states-10m.json is in longitude/latitude, not the projected coordinates of its states-albers-10m.json sibling. A coordinate pair should look like [-88.2, 35.0], not a 0–960 pixel value. If it is projected, the geographic file is the one to use.
  • Decimate before serializing: drop any vertex within ~0.15° of the last one kept, round to two decimals. The texture is 2048px wide — 0.18° per pixel — so this is invisible, and it should bring roughly 25 visited states to well under 100 KB in the inline payload. If it does not, move the decimation into a scripts/prepare-states.mjs writing a committed JSON, mirroring the existing prepare-photos.mjs pattern.
  • TravelGlobe.astro inlines places and only the visited states' shapes into the existing #globe-data script tag. No new fetch, no new runtime dependency.
  • makeAtlasTexture gains one branch: for a country carrying shadeBy: "states", paint every polygon plain and skip isHomelandPolygon entirely, then paint the supplied state rings highlighted on top. Fill rgba(231,144,67,.55) — the visited orange #e79043 softened, because a state is presence rather than a journey — keeping the existing bright hairline stroke.

This solves Alaska and Hawaii for free. Measured against the real 110m topology with a US centroid of 39.8 / −98.6, isHomelandPolygon scores the continental US at 0.00 but Alaska at 28.19 and the Hawaiian islands at 44–59 — well past its 8° limit, so neither would ever shade through the country-level path. As states they shade if and only if they hold a place, and the limit never enters into it.

3. Beam pins

Journey markers — sphere, pulsing ring, stem — stay exactly as they are. Places get their own, much lighter mark:

  • One THREE.LineSegments for every place. Base at r = 1.002, tip at r = 1.045, per-vertex colours running bright at the base to transparent at the tip, depthWrite: false and depthTest: true so the globe occludes the far side. One geometry, one draw call, however many places there are.
  • WebGL draws lines at one pixel regardless of zoom or linewidth. Normally a limitation; here it is exactly the hairline the design wants, and the reason a hundred pins over the continental US stay individually readable at globe scale. No clustering and no level-of-detail logic is needed — the hairline is the density answer.
  • One THREE.Points at the tips (a small round sprite) as the pick target, with raycaster.params.Points.threshold = 0.03 for a forgiving hit radius without visual bulk. Lines are effectively unpickable; points are not.
  • Hover and selection brighten that beam's vertex colours and scale its point, show a DOM tooltip [data-place-label] positioned by projecting the tip to screen — label, formatted date, note — and update the existing #globe-status live region.
  • No camera flight. selectCountry does not move the camera today, and this work should not introduce that.

4. Hub page

Everything lands on the existing hub — src/pages/index.astro and src/components/TravelGlobe.astro:

  • The US country card ([data-country-card="US"]) holds places grouped by state instead of journey articles, each a <button data-place> showing label, formatted date, and note. This is the keyboard path and the no-WebGL path.
  • The country index entry for the US must read “N places · M states”. It needs a branch: the current markup renders {countryTrips.length} journeys · {countryTrips[0]?.dateLabel}, which with zero trips prints “0 journeys · ”.
  • The atlas stats gain a places count beside countries and journeys.
  • The boot default stays Norway — startGlobe selects data.countries[0] — so append the US to the end of countries.
  • Untouched: the “02 / The journeys” section, TripArtwork.astro, [trip]/index.astro, and the photo gallery. Places are not journeys and get no journal pages.

5. Validation and tests

  • Extend validateTravelData in src/scripts/globe-utils.mjs: unique place ids, latitude and longitude in range, date matching ^\d{4}(-\d{2}(-\d{2})?)?$ when present, non-empty state, and a note length cap.
  • New tests in test/travel.test.mjs (npm test, Node's built-in runner): each malformed place is rejected; stateShapes resolves a real state and reports a typo by name; a decimated ring stays within tolerance of the original; formatPlaceDate renders all three precisions.

Adding a place

Once the scaffolding is in, a place is four lines appended to places in src/content/trips.ts:

{ id: "seattle", label: "Seattle", state: "Washington",
  latitude: 47.6062, longitude: -122.3321, date: "2019-07",
  note: "Optional single sentence." },
  • Coordinates to four decimals are plenty — the globe cannot resolve finer.
  • state must match the atlas spelling exactly, or the build fails and names the offender.
  • date and note can both be left out and filled in later.
  • A state shades as soon as one place names it. Nothing else to add.

Build order

  1. 1Data layer. PlaceRecord, the places export seeded with a handful of entries, placesForState, formatPlaceDate, the shadeBy field on CountryRecord, the US country record, and the validation rules with their tests.

    Done. 42 places validate; a deliberately malformed one fails npm run build with Invalid date in branson: summer 2008.

  2. 2State fills. us-atlas devDependency, src/content/us-states.mjs, the payload addition in TravelGlobe.astro, and the shadeBy branch in makeAtlasTexture.

    Done. 25 states shade and the rest of the country stays dark; Alaska and Hawaii are correctly unlit; nothing breaks at the 90°W seam through Missouri. The outlines add 36.0 KB to a 47.4 KB payload — Missouri thins from 224 vertices to 76, and no edge moves more than 0.031°.

  3. 3Beam pins. The LineSegments beams, the Points pick layer, hover and selection, the tooltip, and the live-region announcement.

    Done. Hovering a beam lights it and names it, the pointer moving away falls back to the chosen place, and a beam on the far side cannot be clicked through the planet.

  4. 4Hub copy. The US country card, the country-index branch, and the places stat.

    Done. Every place is a button in the card, the index reads “42 places · 25 states”, and the stats line gained a places count.

Settled while building

  • The homeland work landed first. isHomelandPolygon was committed as 4a60657 before step 2 touched makeAtlasTexture, so the diffs never tangled.
  • Dates read the way the journeys read. The plan said “14 July 2019”; the built formatter says July 14, 2019, matching the existing dateLabel style.
  • formatPlaceDate lives in globe-utils.mjs, not in trips.ts — the tests cannot import the TypeScript module, and validateTravelData already sits there for the same reason.
  • The state file is small. states-10m.json is 114 KB and already in longitude and latitude, so no prepare script and no committed derivative were needed.
  • Home is a field, not a colour. PlaceRecord.home marks where Sean is from; the globe burns that one beam red (#ff2f45) at full opacity down its whole length, clear of both the atlas's amber and Spain's coral trip accent. Amber was tried first and lost against the shaded states — at one pixel wide, a warm hairline on a warm fill is no mark at all.
  • Vertex colours are linear. The tints go through THREE.Color rather than being written into the buffer by hand: an sRGB triple typed straight in renders as rgb(255,219,161) instead of the colour asked for. This will bite the next colour added to the beam layer.
  • The switcher dial keeps its corner. On a phone the place list scrolls past it, so the list is inset 2rem rather than fighting for the spot — the same call the card's actions already made.
