seanmh.com — Search Visibility Execution Plan

Objective: make https://seanmh.com/ the authoritative result for Sean's chosen public name. Repository audit: main@2d47476. Live production audit repeated August 17, 2026. This revision separates what is committed from what is actually deployed.

Primary query set: the exact public-name form the owner chooses, plus qualified variants such as "Sean Higgins software engineer". The bare "Sean Higgins" query is a secondary, long-term objective because it is ambiguous.

Strategy: establish one stable canonical identity, remove duplicate hosts and origins, make the preferred name explicit in visible content, measure through Search Console, and then publish a small number of strong first-hand project pages. Structured data, caching, and social cards support that strategy; none is a magic ranking switch.

Current diagnosis

✗ Production still rotates

e91e744 removed rotation in source, but the Worker was not deployed. Twelve browser-like, cookie-less live requests returned a-scroll 3 times, b-card 5 times, and c-terminal 4 times.

✗ Duplicate host/protocol variants

http://seanmh.com/, http://www.seanmh.com/, and https://www.seanmh.com/ return content instead of permanently redirecting to https://seanmh.com/.

✗ Six indexable origins

Every production *.pages.dev origin returns 200, allows crawling, and lacks X-Robots-Tag: noindex. Nexus also lacks a canonical tag.

✗ Distinct version URLs lack a policy

/?v=nexus and both game URLs return crawlable 200 pages. The games canonicalize to the unrelated résumé homepage and Nexus has no canonical; neither is a sound long-term signal.

✗ b-card and terminal soft-404

Both branches lack a built 404.html. Unknown direct-origin paths—and terminal GET /api/ask—return the profile HTML with 200 instead of a real 404.

! Cache policy is suboptimal, not blocking

Browser-like document responses are private, no-store. That prevents reuse and can hurt performance, but it is not an indexing directive and is not the first SEO blocker.

✗ Identity is underspecified

The canonical homepage title and H1 use “Sean Higgins,” while the stated target is “Sean M Higgins.” There is no structured data and no declared site name.

? Search measurement is unconfirmed

Search Console status is not observable from the repo. Submission is not required for discovery, but Search Console is needed for dependable indexing diagnostics and query measurement.

! One-URL footprint

The sitemap contains only the homepage. The homepage itself is substantive; the weakness is a lack of stable, indexable supporting URLs, not necessarily “thin content.”

✗ No social preview asset

No version emits og:image or twitter:image. The shared headshot can be part of a designed card, but should not simply be used raw.

Corrections to the earlier plan

1. “Committed” is not “shipped.” The stable-default change exists in Git but production still runs the old rotation. Every item now has a live acceptance gate.

2. no-store does not prevent indexing. Improve it after routing and origin control. A careless public-cache change would be worse because one visitor's cookie-selected version could be served to another.

3. Standalone Person markup is not the promised outcome. Use Google's supported ProfilePage pattern with a nested Person; validate supported markup with the Rich Results Test and the complete graph with Schema Markup Validator. Markup must match visible facts.

4. One URL should have one share card. Per-version social images on the same canonical URL would reproduce the identity inconsistency the routing fix is meant to remove. Version-specific cards require distinct stable URLs first.

5. Search Console helps measurement, not basic discovery. Submitting a sitemap and requesting a recrawl are hints, not guarantees. Use URL Inspection and performance reports instead of treating site: searches as the primary acceptance test.

6. More pages is not automatically better. Do not publish all wiki files wholesale. Start with a few useful, first-hand case studies that are safe to disclose, internally linked, and independent of the version cookie.

7. Canonical is for duplicates, not disposal. b-card and c-terminal can consolidate to the homepage because they represent substantially the same profile. Nexus and the games should not claim that the résumé homepage is their canonical equivalent. Noindex them for now, or later give them stable path URLs and self-canonicals.

Router precedence

  1. Normalize the public host/protocol with the one-hop 308.
  2. Dispatch /api/* and apply the API-wide noindex/security headers.
  3. Serve version-independent control routes and future path-owned content such as /projects/*.
  4. For remaining proxied routes, validate v, then resolve valid v → valid pv → a-scroll.
  5. Fetch the chosen Pages origin, strip origin-only X-Robots-Tag from every response, then apply the public URL's own robots/cookie/cache policy.

This order preserves the existing API contract, prevents cookies from changing site-wide files or canonical project pages, and makes the Worker the sole authority for robots signals on seanmh.com.

Critical rollout rule: deploy and test the Worker's X-Robots-Tag stripping before adding noindex to any Pages origin. Do not disallow those origins in robots.txt; a blocked crawler cannot see the noindex directive. Canary one origin first and confirm that the direct origin says noindex while every proxied apex resource—including images and other non-HTML assets—has the origin-only header removed. If any clean apex response returns noindex, stop the rollout and roll back before deploying the other branches.

Use Cloudflare Pages placeholders rather than enumerating deployment hostnames in every branch:

https://:project.pages.dev/*
  X-Robots-Tag: noindex

https://:version.:project.pages.dev/*
  X-Robots-Tag: noindex

Safe release batches

  1. Release A — parity: deploy the already-tested stable-default Worker by itself and prove production no longer rotates.
  2. Release B — guardrails: deploy host redirects, strict ?v= handling, URL-level noindex rules, origin-header stripping, and deterministic SEO control routes. Test all of them before touching a Pages origin.
  3. Release C — branch hygiene and origin canary: add real 404 pages to b-card/c-terminal, add _headers to one low-risk origin, verify status/noindex behavior and apex header stripping, then deploy the other five origins in small batches.
  4. Release D — identity: deploy the chosen name, shared SEO head contract, and structured data across the required layouts; update approved external profiles in parallel. The social card may ride with this batch if ready, but does not block it.
  5. Release E — content: launch the path-owned project hub and first case studies only after routing, sitemap generation, and metadata tests pass.

Before each batch, confirm every affected worktree is clean or that unrelated local files are intentionally excluded. Record commit, Pages deployment, Worker deployment, smoke result, and rollback target. Roll back immediately if the clean apex rotates, redirects incorrectly, or returns noindex.

Local parity: mirror version allowlisting, invalid-parameter behavior, cookie semantics, cache policy, and future path ownership in scripts/dev-proxy.mjs. HTTPS/www redirects and Pages-origin header stripping are production-edge concerns, but their Worker behavior still needs unit coverage.

Required preflight: on main, run the Worker tests, shared-contract check, and Wrangler dry run under the repository's Node version. On every changed version branch, run its type/static check, production build, and any branch-specific tests. Do not start a Pages or Worker deployment with a failing or skipped check.

Minimum viable SEO release: complete every P0 item plus the P1 public-name decision and visible identity update. Do not hold that release for social artwork, project case studies, optional query-URL cleanup, or AI-crawler policy. Those improve the result later but are not prerequisites for a stable, measurable canonical profile.
